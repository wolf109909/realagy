# Architecture

`agy acp` runs the agent: it generates text and reasoning and decides which tools to use. Pi owns the transcript and rendering, and its active tools are offered alongside agy's own.

## Process and models

The extension starts one long-lived `agy acp` process per pi session (`src/acp/driver.ts`). It shares the Antigravity CLI's sign-in, settings, and data dir (`~/.gemini/antigravity-cli`). On startup realagy:

1. finds `agy` (`AGY_BIN` > `PATH` > `~/.local/bin/agy`). If none is found, it points to `/agy setup` and stops there;
2. sets `queuedMessages` to `send-immediately` in agy's `settings.json` when it is unset, so pi steering interrupts the agent the way pi expects;
3. reads the live model catalog from `session/new` and registers it as `antigravity/*`. Effort tiers (`-low`, `-medium`, `-high`) collapse into one pi model with thinking levels (`src/models.ts`).
4. applies the independent Pi-side metadata settings: `REALAGY_CONTEXT_WINDOW` (default 256,000) and `REALAGY_MAX_OUTPUT_TOKENS` (default 64,000). They affect pi's planning and compaction only, not agy's real model limits. `/agy settings` (`src/settings.ts`) edits those values and the bypass in one menu. Save writes `~/.pi/agent/realagy/settings.json` atomically with user-only permissions; saved values override environment defaults per field. Saving re-registers model metadata immediately. A bypass change calls `AcpDriver.restart()`, which closes the current connection/proxy but preserves background watchers and resumes remembered sessions on the next turn.

With the bypass enabled in the menu or with `REALAGY_NO_COMPACT=1`, the driver first starts a loopback Cloud Code reverse proxy (`src/acp/catalog-proxy.ts`) and adds `--cloud_code_endpoint http://127.0.0.1:<port>` to agy's arguments. The proxy buffers only successful `fetchAvailableModels` responses. It sets every `CASCADE_USE_EXPERIMENT_CHECKPOINTER*` configuration's `enabled` to false and `max_token_limit` above the model window, and raises the containing model's catalog `maxTokens` so agy cannot clamp the checkpointer back to `maxTokens - maxOutputTokens`. All three changes are required (verified with GPT-OSS over 80k tokens). Other requests and responses, including chunked generation requests and SSE responses, stream through unchanged. Undici supplies direct and HTTP(S) CONNECT upstream proxy support with `NO_PROXY` handling. No TLS CA or external proxy process is involved. The proxy is shared across agy respawns and closes with the driver. Real server-side limits still apply: an over-limit request fails rather than triggering agy's local summary.

Each spawn runs `agy acp --agent realagy-<hash>`, a hidden custom agent profile that realagy writes to `~/.gemini/config/agents/realagy-<hash>.md` (`src/agent-profile.ts`, `GEMINI_HOME` respected). It replaces agy's whole system prompt: agy's ACP `_meta.antigravity.systemPrompt` only supports `append`, and the agent is chosen per process (`--agent`), never per session. The profile's frontmatter sets `hidden: true`, so normal agy sessions do not offer it as a subagent (`agy agents` still lists it), and `excludeDefaultComponents: true`, so agy adds none of its own sections (identity, artifacts, communication style with its mandatory `file://` links, slash commands, subagents, skills, user rules, user information) and none of its native file, shell, subagent, or scheduling tools; only `manage_task`, `list_resources`, and `read_resource` remain. The body is realagy's own short system prompt (pi's system prompt and transcript arrive in the prompt; use pi's tools; plain-path formatting). Its `mcpServers` entry names `pi-bridge` with every bridged tool marked `eager`: under a custom agent agy ignores `eagerMcpServers`, and the entry overlays the server passed over ACP (no URL or token is written to disk), so pi tools stay native `mcp_pi-bridge_<tool>` tools without permission prompts. `<hash>` covers the file content, so pi instances with different tool sets never overwrite each other's profile. Each turn refreshes the file's mtime, profiles unused for 7 days are deleted, and when the bridged tool set changes the next turn respawns agy with the new profile (warm sessions resume in the new process). `REALAGY_AGY_PROFILE=0`, or a profile that cannot be written, keeps agy's default agent and its own prompt and tools (see Tools).

The provider is registered with ambient-only auth: there is no `login` method, pi never stores a key, and the provider counts as configured whenever agy is present. agy offers Claude/GPT only to clients it recognizes, so `initialize` sends `clientInfo.name = "zed"`.

Starting the process is single-flight: concurrent callers (startup catalog discovery, `/agy setup`, and the first turn) share one spawn and one `initialize` handshake, so no request ever reaches agy before the handshake completes. If agy cannot be spawned, or exits mid-turn, the turn fails with the binary path, exit code or signal, and agy's last stderr line (secrets redacted), and the next turn respawns it. agy exits on its own when its stdin closes, so it never outlives pi.

## Turns, aborts, and timeouts

Turns are serialized on the one process. Esc sends ACP `session/cancel` as a notification: agy ends the prompt with `stopReason: "cancelled"` and both the process and the session stay alive. The process is torn down only when agy has not settled the cancelled prompt within 10 seconds. An abort that arrives before the prompt was sent settles the turn at once; the remaining setup steps stop without sending it. Teardown, the 5-minute inactivity guard, and the cancel safety net only ever act on the process of the turn they belong to, never on a later turn's.

A turn parked on pi tool calls waits for pi's tool results. If pi starts a new turn instead of returning them (its agent loop ended after the `toolUse` message), realagy cancels the orphaned turn and fails its parked calls rather than queueing the new turn behind it.

Esc while a pi tool (such as `bash`) runs aborts the same signal the ACP turn was started with, so the driver cancels the parked turn at once. When the turn settles aborted, every parked call of it is failed, including slow calls already escalated to `bridge_poll_result`, so no round-trip outlives its turn. Pi then hands the aborted tool result back with its signal already aborted; realagy delivers it to the turn if that turn is still settling, and otherwise ends the message as aborted without planning or starting another turn.

An aborted turn keeps its progress. The session holds everything agy recorded before the cancel, so realagy records a warm checkpoint for it (see below) when agy stored the turn's prompt: the conversation store has a user-input step (`step_type` 14) newer than the turn's starting step. agy writes that step as soon as the prompt arrives, so even a cancel before any output counts; a turn aborted before its prompt was sent records nothing. `continue` (or any next message) after Esc then goes to the same ACP session as a delta, on the first turn of a session too. With transcript parts (below), the user-input step that counts is the one of the last part, which carries the real prompt.

## Tools

Pi's tools are served by a loopback MCP server (`src/mcp-server.ts`) that requires a shared-secret header. It lists every registered pi tool that pi declares to models when active (`direct` and `model-only` exposure, active or not), plus any other tool that is currently active (`src/bridge-catalog.ts`). Extensions activate and deactivate tools during a session (pi-lens's situational tools through `pi_lens_activate_tools`, for example), and agy keeps the tool list a session started with, so a tool activated later is already listed and callable in the running session. Calls are dispatched only for tools pi has active at that moment; any other call returns an error naming the active pi tools. Because the list does not follow activations, it stays the same across turns and sessions and does not break agy's prompt cache. The server is registered with every ACP session as the eager `pi-bridge`, so models see pi tools directly instead of going through agy's lazy `call_mcp_tool` helper. Request bodies are decoded only once complete, so multi-byte characters split across network chunks arrive intact, and each tool's input schema is normalized once per tool definition rather than on every MCP request.

Every `session/new`, `session/resume`, and `session/load` appends a tool policy to agy's system prompt (`_meta.antigravity.systemPrompt.append`; `src/tool-policy.ts`). With the agent profile it only names the pi tools the bridge lists and how agy exposes them (`mcp_pi-bridge_<tool>`), because the profile already removed agy's own tools and prompt.

Without the profile (`REALAGY_AGY_PROFILE=0`, or it could not be written), agy keeps its native tools (`read_file`, `run_command`, `write_file`, `edit_file`, `search_web`, `invoke_subagent`, …): `agy acp` 1.5 ignores tool allowlists (`enabledTools` / `disabledTools`). Instead, the appended policy (agy advertises `systemPrompt.append` in `initialize`) names the pi tools the bridge lists and asks the model to use them for all file and shell work (reading files including images, every shell command, changing files), not to use agy's built-in `run_command`, `read_file`, `write_file`, or `edit_file` for anything a pi tool can do, and to work itself in the foreground instead of starting subagents, the browser agent, background tasks, or scheduled tasks (`invoke_subagent`, `define_subagent`, `manage_subagents`, `schedule`, `manage_task`); a native tool is for jobs no pi tool can do (such as `search_web`). Naming agy's tools matters: with only "prefer pi's tools", GPT-OSS kept mixing in native calls, while Gemini and Claude follow either wording. It also overrides agy's communication-style and artifact rules on file links (see below). The policy never appears in the user's prompts. It names the same tools the bridge lists, so it matches the tools every session offers, and activating a tool never changes the policy text. Native tools stay usable: they run inside agy under its own permission rules (`~/.gemini/antigravity-cli/settings.json`), and realagy approves agy's permission requests. Each turn sets the ACP session mode to agy's `default` (pi's `plan` maps to agy's `plan`; agy 1.5 offers only `default`, `accept-edits`, and `plan`), so agy asks before every native command or edit and each request goes through realagy's permission handler, which approves it.

File references reach pi as plain paths. agy's default prompt requires `[utils.py](file:///abs/utils.py#L10-L20)` links, which pi's TUI renders as `utils.py (file:///abs/utils.py#L10-L20)` on terminals without OSC 8 hyperlinks. The profile prompt (or, without it, the policy) asks for plain paths relative to the working directory (`src/a.ts`, `src/a.ts:10-20`) and inline code for symbols. As a safety net for resumed sessions whose history is full of such links, the reply stream rewrites them (`src/file-links.ts`, chained after the `<SYSTEM_MESSAGE>` filter in `TextAccumulator`): a `file://` link whose label is a code symbol becomes the label; a label that already holds a path stays, gaining `:10-20` from the `#L10-L20` fragment; a bare-basename label becomes the decoded path, relative to the turn's working directory when it lies inside it. Backticks around the label are kept, image links (`![…](file://…)`) and links inside inline code or fenced code blocks are left alone, and links split across stream chunks are held until complete (at most 2 KB).

Native tool use is always visible in pi (`src/native-tools.ts`):

- Each native call agy finishes during a turn adds a line to the reply's thinking block, such as `agy → run_command npm test ✓ 2.1s` or `agy → read_file src/provider.ts ✗`. The duration is left out under 0.1 s: agy reports reads only after they finished, so their start and end arrive together. Calls of agy's own MCP servers count as native; `pi-bridge` calls are pi tool calls and render as pi tool cards instead. Thinking is excluded from warm-session fingerprints and from the transcript sent to agy, so these lines never affect session reuse; reply text they split is joined back into one reply when a fresh session replays the transcript.
- While agy works on its own, a live panel above pi's editor lists every running item with a spinner and its elapsed time: native calls of the current turn (`⠹ agy  run_command  npm test  12s`), commands agy moved to the background (`background`), and subagents (`subagent`). Items leave the panel when they finish, or when the agy process that ran them exits; the panel disappears when nothing runs. It is a widget component mounted once per burst of work: a 100 ms timer turns its spinner and asks pi's TUI for a redraw (pi coalesces redraws), only while items run. RPC mode ignores component widgets, so RPC clients do not get the panel; they still get the thinking lines and the background cards. While a native call of the current turn runs, the 5-minute inactivity guard pauses, because a long native command produces no ACP frames.
- A call still running when the prompt ends (agy backgrounds commands after `WaitMsBeforeAsync`) gets the line `agy → <tool> <target> … (runs in background)`; `invoke_subagent` returns at once and gets `✓ … (runs in background)`.

agy finishes background work on its own: it writes a message to `brain/<sessionId>/.system_generated/messages/<id>.json` and runs an autonomous agent turn. ACP sends nothing while no prompt is in flight, so realagy polls that directory (every 2 seconds, only while the session has unfinished background work, for at most 12 hours) (`src/acp/background.ts`). The messages of one poll become one pi custom message (`agy-background`) sent with `deliverAs: "followUp"` and `triggerTurn: true`: an idle pi agent starts a turn right away, a busy one gets it after its current work. So pi's agent is told, the result stays in pi's transcript (custom messages reach the model as user messages), and it survives model switches, `/tree`, compaction, and fresh agy sessions. The model sees the tool, its target, agy's title for the task, the exit code, how long it ran, the last 80 lines (at most 8 KB) of output, and the path of agy's full task log. pi renders the message as a tool card in the style of realtasks' task notifications (`src/background-card.ts`): one card per message with pi's custom-message background (`customMessageBg`), one line of vertical padding and the user's `outputPad`. Each item gets a header `✓ agy task Sleep and print DONE finished · exit 0 · 15s` (`agy subagent <name>` or `agy message <title>` for the other kinds; `✗` in the error color on failure), then its output in the `toolOutput` color. Collapsed, the output shows its last 5 lines under `... (N earlier lines, ctrl+o to expand)`, like pi's `bash` card; expanded, it adds the command line under the header (`$ <command>` for `run_command`, `<tool> <target>` otherwise, agy's title for a subagent), the whole captured output and the `log:` path. Several items of one message are separated by a blank line. A subagent's card shows its reply instead of command output. A left click anywhere on the card, padding included, toggles just that card, like a click on a pi tool card (only in pi's fullscreen mode, where pi owns the mouse; ctrl+o is the keyboard path). The click state is kept per message object, so redraws keep it, until the global expand toggle changes: then every card follows the global state again. agy's own autonomous reply to the same event is dropped (below), so the event is answered once, by pi's agent. Tracked work is forgotten when the agy process exits, because its background tasks end with it. agy flushes the frames it buffered meanwhile (the task's completion and its autonomous reply) at the start of the next `session/prompt`, before echoing the new prompt as `user_message_chunk`. realagy holds every frame that arrives before that echo and drops them once the echo arrives, so the leftovers never leak into the new reply. If a prompt ends without an echo, the held frames are processed normally, so nothing is lost on servers that do not echo. agy's own "⚠ Model produced invalid output." notice (sent as reply text when a model, typically GPT-OSS, emits a malformed tool call that agy then retries) is shown as thinking, so it never becomes part of the stored answer.

A pi tool call follows this path:

1. agy calls a pi tool over MCP. The request is parked.
2. realagy emits a genuine pi `toolCall` and ends the assistant message with `toolUse`.
3. Pi runs the tool under its normal permission policy and hooks.
4. Pi's `toolResult` answers the parked MCP request — appending any user steering messages and images queued while the tool ran as a `<pi-steering>` block — and the same ACP turn continues.

`agy acp` times out an MCP `tools/call` HTTP request after 180 seconds. After 150 seconds (`ESCALATE_AFTER_MS`), a still-running pi tool returns a `STILL RUNNING` handle that the model resolves through `bridge_poll_result`. Each `bridge_poll_result` request long-polls for up to another 150 seconds, waking immediately when the tool finishes, so multi-minute or multi-hour foreground tools never hit the 180-second MCP deadline or spin in a tight polling loop. While pi is still executing an escalated tool, no hard timeout kills the call. If agy stops polling and ends its prompt before the pi tool finishes, realagy records the warm checkpoint at the `toolUse` message and delivers the late `toolResult` on the same ACP session as a `pi://transcript-delta` continuation.

## Images

Pi image results go back as ordinary MCP image blocks. agy stores them under its conversation (`brain/<session>/.system_generated/steps/<n>/media_*.png`) and shows them to the model, so the same ACP session continues and no history is replayed. This works with pi's `read` tool on Gemini and Claude. Images in pi's transcript are sent as ACP image blocks when a fresh session starts. GPT-OSS models are text-only (they cannot see images even through agy's native `read_file`), so they are registered without image input.

## Session reuse and prompt caching

Every new user turn is planned from pi's current transcript (`src/transcript.ts`).

- **Warm:** a checkpoint on the branch (see below) still matches the messages its session holds, and the cwd is unchanged. realagy reuses the ACP session and sends only the messages pi added since. Plain user messages go as ordinary prompt text. Anything else (other models' replies, tool results, updated pi system instructions, a changed active tool set) goes as a `pi://transcript-delta` resource. A changed tool set is listed in the delta as `<pi-tools-update>`; it never forces a new session, because the bridge already lists every tool an extension can activate. agy's native history stays an unchanged prompt prefix the provider can cache.
- **Fresh:** after manual `/compact`, a cwd change, a switch to an agy model with no checkpoint on the branch, or a failed turn with no matching checkpoint, realagy starts a new session and sends the transcript as `pi://transcript`.

Checkpoints are recorded at every point where realagy knows what the ACP session holds:

- when a turn completes;
- at each pi tool boundary: when agy calls a pi tool, the session holds the transcript up to that `toolUse` message. This checkpoint lives in memory only and is replaced by the turn's later checkpoints;
- when a turn is aborted after agy stored its prompt (Esc during a streaming reply, a native command, or a pi tool). The checkpoint covers the transcript up to the aborted assistant message: the last `toolUse` message when the turn ended while pi still ran the tool, or the partial reply pi recorded;
- when agy ends a turn while an escalated pi tool still runs (below).

So the user, `assistant` (`toolUse`), `toolResult`, and aborted `assistant` messages of an interrupted turn are either already in the session or sent as the delta of the next turn, whether Esc came on the first turn or in the middle of a multi-step tool loop. A turn's tool-boundary checkpoint is replaced by its next checkpoint, so the list grows by one entry per turn. Only settled turns (completed or aborted) are persisted, so the session file does not grow with every tool call.

Each completed or aborted turn persists its last checkpoint as a `realagy-warm-session` entry (`sessionId`, `maxStepIdx` in `~/.gemini/antigravity-cli/conversations/<sessionId>.db`, message keys, system prompt, and tools) in the pi session tree. Across `/reload`, `pi -c` / `/resume`, and `/tree` branch switches, realagy restores the checkpoints from the session file and resumes the matching ACP session directly. When `/tree` rewinds to an earlier turn whose `<sessionId>.db` has already advanced past that turn's `maxStepIdx`, realagy forks `<sessionId>.db` into a new `<forkedSessionId>.db` truncated to `idx <= maxStepIdx` (`src/acp/step-usage.ts`) so the resumed session continues from that exact point in history while leaving the other branch's store intact. The stores run in SQLite WAL mode, so the fork is taken with `VACUUM INTO`, a consistent snapshot that includes steps still in the `-wal` file; copying the `.db` file alone would drop them. A checkpoint of an aborted turn carries the store's highest step at the cancel, so `continue` resumes the store as it is, and a later `/tree` rewind to that point forks it there.

`/tree` restores pi's tool loadout from the target branch (`_restoreToolsFromTranscript()`). Pi also activates every registered extension tool that the branch never mentions in its tool declarations, on the assumption that it was installed later. Situational tools that an extension keeps inactive (pi-lens registers five and activates them on demand) are such tools, so a rewind would activate them and pi's next request would add a `<tools>` system message declaring them. realagy records the active tools on `session_before_tree`. On `session_tree` it deactivates every tool that the navigation activated, that was inactive before it, and that the target branch never declared. This restores the branch's recorded tool set, the one its checkpoints hold as `tools`. Tools that were already active, such as those of a newly installed extension, stay active as pi intends.

Planning compares the transcript against every restored checkpoint. Per-message keys and the fingerprint of every transcript prefix are computed once per turn, and the full `pi://transcript` (also the fallback of a warm plan) is serialized once, so planning stays linear in transcript size however many checkpoints the session has.

`agy acp` truncates a single `session/prompt` payload past 192 KB from the end, which would cut off recent turns and the user's latest prompt. A `pi://transcript` or `pi://transcript-delta` larger than 160 KB is therefore delivered in parts of at most 160 KB each, split at line boundaries (`src/transcript.ts`). This happens, for example, after switching to an agy model in the middle of a long session, or after another model's long run. The driver sends each earlier part as its own `session/prompt` on the turn's session, asking the model to reply only `OK` without using tools, and then sends the last part with the real prompt. While parts are being delivered, the replies are dropped, pi tool calls are refused, and an abort cancels the part in flight. The full transcript reaches the session, and each part reuses the cached prefix of the ones before it. Every part but the last is at least 90% full, and up to 8 parts (about 1.15 MB of transcript) are sent; past that, `<pi-system>`, any leading `<realctx-history>` summaries, and the newest messages are kept intact, while older middle messages collapse into a `<pi-transcript-omitted>` marker. Attached images ride with the last part, numbered across the whole transcript.

A remembered session that is not live in the current process is resumed with `session/resume` when agy advertises it (`sessionCapabilities.resume`), which restores the history without replaying it; otherwise `session/load` is used and its replayed history is dropped. `session/load` of an unknown id silently returns an empty session, so a remembered session whose `<sessionId>.db` no longer exists counts as lost before agy is asked. A lost session, or a failed resume or load, makes the driver open a new session and send the full transcript, not the delta. Warm-session matching is designed to coexist with arbitrary pi `context` extensions without per-extension special cases: fingerprints exclude model-private thinking, key `toolResult` messages by structural identity (`toolName`, `toolCallId`, `isError`) rather than mutable body text, key `user` messages by their primary prompt text (tolerating appended `{ type: "text" }` context blocks, dropped historical images, and line-bounded prompt headers/trailers added only while a prompt is active), skip unpersisted transient `user` messages injected alongside a turn's prompt once that turn moves into history, and match the intact suffix of recent turns when a context manager compresses or drops older turns into fewer leading summary messages ($0 \le \text{lead} < \text{drop}$). A continuation after a pi tool result always re-enters the running ACP turn and records its warm checkpoint from the turn's final transcript state.

## Usage, context, and quota

`agy acp` reports usage only once per prompt, summed over all of its internal model calls. Exact per-call counts live in agy's conversation store, `~/.gemini/antigravity-cli/conversations/<sessionId>.db`. Agent steps (`step_type` 15) carry metadata field 9: 2 = uncached input, 3 = output, 5 = cache read. `src/acp/step-usage.ts` reads the steps that are new since the last report, both when a tool call ends a pi message and when the prompt ends.

| pi `Usage` field | Source |
| --- | --- |
| `input`, `cacheRead`, `output` | Sum over the model calls the pi message covers, so pi's footer shows real `↑ R ↓` and `CH` |
| `totalTokens` | Context held by the latest model call. Pi's footer, `ctx.getContextUsage()`, and compaction use it as current occupancy |
| parallel tool calls | One model call can request several tools, and each becomes its own pi `toolUse` message. The first carries the call's usage. Each sibling carries a 100-token placeholder split by the same cache ratio, plus the same context size, so pi's per-message `CH` and context bar don't drop out. `/agy usage` ignores placeholders |
| fallback | ACP `usage_update.used` for occupancy when no step was measured |
| none | Zero usage, so pi estimates the message itself. realagy never puts regex estimates or turn-cumulative totals into `totalTokens` |

The turn-cumulative `PromptResponse.usage` (`inputTokens`, `outputTokens`, `thoughtTokens`, `cachedReadTokens`, `cachedWriteTokens`, `totalTokens`) fills `input`, `output`, `cacheRead`, and `cacheWrite` only for a message that no step measured but that has an occupancy, and its total is kept as `usage.agyCumulativeTotalTokens`. realagy computes no client-side token estimates.

Quota comes from the live `agy acp` process's local Language Server ConnectRPC endpoint (`POST http://127.0.0.1:<port>/exa.language_server_pb.LanguageServerService/RetrieveUserQuotaSummary` with `{"forceRefresh":true}`, discovering and caching `<port>` per PID from `~/.gemini/antigravity-cli/log/acp-server-*-<pid>.log`), falling back to `agy --print /usage --output-format json` when no live ACP server port is available (`src/quota.ts`). agy groups models by quota (Gemini; Claude and GPT; dedicated groups such as Argon), each with a 5-hour and a weekly bucket. `/agy usage` fetches it on demand (~0.3 s via the live ACP server, or ~5–10 s via the CLI fallback): it shows a cancellable `BorderedLoader` in TUI mode without flashing stale results first, resolves the CLI fallback as soon as agy flushes its JSON line to `stdout` (without waiting for its internal language server to finish shutting down), and prints a single Claude-style report with session cache-hit stats, each model group's description, `Current session (5h)` and `This week` `━`/`─` usage bars (`% used`, rounded up to `0.1%` so any non-zero usage never reads `0%`), and weekday + relative countdown reset subtitles (`Resets today 16:20 (in 58m)`, `Resets Friday 01:45 (in 6d 10h)`, or `Starts with your first message` / `Quota available` when unused). Quota is never polled in the background. When agy replies with its fixed "Usage Limit Reached" notice, the turn fails with an explicit quota error instead of passing it off as an answer. Likewise, when agy's whole reply is its "⚠ Our servers are experiencing high traffic right now…" notice, the turn fails with `Antigravity servers are overloaded: …`, which pi treats as a retryable provider error and retries automatically.
